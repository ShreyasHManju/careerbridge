# CareerBridge — ₹0 Self-Hosted Deployment Guide

**Target Audience:** Developers, Students, and Operators running CareerBridge on local hardware or self-hosted servers with zero cloud infrastructure cost.  
**Supported Deployment Modes:** Localhost, Private LAN, and Cloud Object Storage.  
**Topology:** Single-Node Docker Compose (`postgres:16` + `FastAPI` + `nginx:alpine` SPA) with local persistent volume storage.

---

## 1. System Requirements & Prerequisites

Before deploying CareerBridge locally, ensure your host environment meets the following baseline requirements:

* **Operating System:**
  * **Linux:** Ubuntu 22.04+, Debian 12+, Arch Linux, Fedora, or any standard distribution with Docker Engine.
  * **Windows:** Windows 10/11 with Docker Desktop and WSL2 backend.
  * **macOS:** macOS Monterey (12)+ with Docker Desktop (Apple Silicon or Intel).
* **Software:**
  * **Docker Engine:** Version 24.0+ (or Docker Desktop 4.20+)
  * **Docker Compose:** Version 2.20+ (`docker compose` CLI plugin)
  * **Git:** Version 2.30+
* **Hardware Sizing:**
  * **RAM:** 4 GB minimum (8 GB recommended for optimal multi-container performance).
  * **Disk Space:** 10 GB free disk space for Docker images, PostgreSQL database data, and student file uploads.
* **Network Access:** Local loopback interface (`127.0.0.1`), plus local Wi-Fi / Ethernet access if LAN testing is desired.

## 2. Deployment Architecture

CareerBridge self-hosted architecture uses a hardened 3-tier container topology running on an isolated internal Docker bridge network:

```
                  [ Client Web Browser ]
                            │
                            ▼ (Port 80 or 8080)
             ┌──────────────────────────────┐
             │   frontend (nginx:alpine)    │
             │   - Serves React SPA assets  │
             │   - Injects security headers │
             │   - Proxies /api/* & /health │
             └──────────────┬───────────────┘
                            │
                            ▼ Internal Network (backend:8000)
             ┌──────────────────────────────┐
             │   backend (FastAPI/Uvicorn)  │
             │   - Runs as non-root appuser │
             │   - Security gate validation │
             │   - Streams & validates files│
             └──────┬────────────────┬──────┘
                    │                │
                    ▼                ▼
   ┌──────────────────────┐    ┌───────────────────────────────────┐
   │ db (postgres:16)     │    │ /app/uploads                      │
   │ Named Docker Volume: │    │ Named Docker Volume:              │
   │ careerbridge_        │    │ careerbridge_uploads_production   │
   │ postgres_production_ │    │ (Persistent local resumes/images) │
   │ data                 │    └───────────────────────────────────┘
   └──────────────────────┘
```

### Core Architecture Invariants:
1. **Zero External PostgreSQL Exposure:** Port `5432` is attached only to the internal Docker bridge network. No database port is exposed on the host.
2. **Backend Loopback Isolation:** The backend ASGI server binds exclusively to `127.0.0.1:${BACKEND_PORT:-8000}:8000` on the host, preventing direct unproxied access from external networks.
3. **Single Ingress Point:** The frontend Nginx container serves as the reverse proxy for all web traffic, API routing, and health checks.

## 3. Environment Configuration (.env)

CareerBridge requires environment variables to configure security, database credentials, CORS policies, and storage providers.

### Step 1: Copy the Template
```bash
cp .env.example .env
```

### Step 2: Configure Production Parameters
Edit `.env` with your preferred editor and set the required variables:

```env
# 1. Application Mode
ENVIRONMENT=production
DEBUG=False
PROJECT_NAME="CareerBridge"
API_V1_STR="/api/v1"

# 2. Host Port Bindings
BACKEND_PORT=8000
FRONTEND_PORT=80

# 3. Security Credentials (MUST be generated by operator)
JWT_SECRET_KEY=replace_with_a_secure_random_hex_key_at_least_32_characters_long
JWT_ALGORITHM=HS256
ACCESS_TOKEN_EXPIRE_MINUTES=30
GOOGLE_CLIENT_ID=your_google_oauth_client_id.apps.googleusercontent.com

# 4. Database Credentials
POSTGRES_USER=postgres
POSTGRES_PASSWORD=your_strong_generated_db_password_here
POSTGRES_DB=internship_db

# 5. Storage Provider (₹0 Self-Hosted Local Mode)
STORAGE_PROVIDER=local
UPLOAD_DIR=uploads
MAX_UPLOAD_SIZE_MB=5
MAX_RESUME_SIZE_MB=5
MAX_PROFILE_IMAGE_SIZE_MB=2

# 6. CORS Allowed Origins (Comma-separated or JSON list)
BACKEND_CORS_ORIGINS="http://localhost:80,http://127.0.0.1:80,http://localhost:8080,http://127.0.0.1:8080"

# 7. Notifications
EMAIL_PROVIDER=local
```

### Generating Strong Cryptographic Secrets:
* **Linux / macOS / Git Bash:**
  ```bash
  # Generate JWT secret key:
  openssl rand -hex 32
  # Generate PostgreSQL password:
  openssl rand -hex 24
  ```
* **PowerShell (Windows):**
  ```powershell
  # Generate random 64-character secret:
  -join ((65..90) + (97..122) + (48..57) | Get-Random -Count 64 | ForEach-Object {[char]$_})
  ```

> [!WARNING]
> Never commit your `.env` file to version control. The `.env` file is excluded in `.gitignore` by default.

## 5. Database Initialization & Schema Migrations

CareerBridge utilizes Alembic for transactional database migrations. Migrations **must** be executed against a healthy PostgreSQL instance before starting the backend and frontend services.

### Step 1: Start PostgreSQL and Wait for Health Status
```bash
docker compose -f docker-compose.production.yml up -d db
```

Wait until the database container reports `healthy`:
```bash
docker compose -f docker-compose.production.yml ps db
```

### Step 2: Execute Database Migrations to Head
```bash
docker compose -f docker-compose.production.yml run --rm backend alembic upgrade head
```

### Step 3: Launch Full Multi-Container Topology
```bash
docker compose -f docker-compose.production.yml up -d
```

### Why Migrations Must Precede Application Startup:
FastAPI models expect the complete PostgreSQL schema (tables, foreign keys, indexes, and constraints) to exist. Running migrations beforehand guarantees that backend readiness probes (`/health/ready`) pass immediately on boot.

## 7. Data Persistence & Volume Management

Self-hosted deployments rely on two dedicated Docker named volumes:

1. **`careerbridge_postgres_production_data`:** Contains the physical PostgreSQL 16 database clusters, tables, users, and relational records at `/var/lib/postgresql/data`.
2. **`careerbridge_uploads_production`:** Contains uploaded candidate resumes (`/app/uploads/resumes`) and profile avatars (`/app/uploads/profile_images`).

### Volume Lifecycle Rules:
* Running `docker compose down` stops and removes containers and networks, but **preserves all named volumes intact**.
* Restarting containers (`docker compose restart` or `docker compose up -d`) automatically re-attaches existing data volumes.
* **DO NOT** run destructive commands such as `docker compose down -v` or `docker volume prune` unless you intentionally intend to wipe all uploaded documents and database records.

> [!NOTE]
> Persistent Docker volumes protect against container recreations, but they do **not** replace a backup strategy. For long-term deployments, schedule database dumps using `pg_dump` and periodic archive copies of the `/app/uploads` volume.

## 8. Deployment Profiles

### 8.1 Profile 1: Localhost Mode
Localhost mode is designed for single-machine local use (browsing from the same laptop or workstation).

* **Access URL:** `http://localhost` (or `http://127.0.0.1`)
* **Port Conflict Handling:** If port `80` or `8000` is already in use by host services (e.g., IIS, Apache, local dev servers), adjust ports in `.env`:
  ```env
  FRONTEND_PORT=8080
  BACKEND_PORT=8001
  ```
  Then access CareerBridge at `http://localhost:8080`.

---

### 8.2 Profile 2: LAN Mode (Local Network Testing)
LAN mode allows other devices on your home or office local network (e.g., mobile phones, tablets, or testing laptops) to access CareerBridge.

```
 [ Phone / Laptop on Wi-Fi ]
              │
              ▼ HTTP (http://192.168.1.50:8080)
 ┌──────────────────────────────────────────────┐
 │ Host Machine (192.168.1.50)                  │
 │ - Port 8080 allowed through Host Firewall    │
 │ - Nginx container receives request           │
 │ - Nginx proxies /api/* internally to backend │
 └──────────────────────────────────────────────┘
```

#### Step 1: Discover Host LAN IP Address
* **Linux / macOS:** `ip addr` or `ifconfig` (e.g. `192.168.1.50`)
* **Windows (PowerShell):** `Get-NetIPAddress -AddressFamily IPv4 | Where-Object InterfaceAlias -notlike "*vEthernet*" | Select-Object IPAddress`

#### Step 2: Configure CORS for the LAN IP in `.env`
Update `BACKEND_CORS_ORIGINS` to include your host machine's LAN IP:
```env
FRONTEND_PORT=8080
BACKEND_CORS_ORIGINS="http://localhost:8080,http://127.0.0.1:8080,http://192.168.1.50:8080"
```

#### Step 3: Configure Host Firewall
Allow inbound TCP traffic on port `8080` from your local subnet:
* **Linux (UFW):**
  ```bash
  sudo ufw allow from 192.168.0.0/16 to any port 8080 proto tcp comment 'CareerBridge LAN Testing'
  ```
* **Windows (PowerShell as Admin):**
  ```powershell
  New-NetFirewallRule -DisplayName "CareerBridge LAN 8080" -Direction Inbound -LocalPort 8080 -Protocol TCP -Action Allow
  ```

#### Security Boundaries in LAN Mode:
* **Backend Isolation:** Backend port 8000 and PostgreSQL port 5432 remain strictly internal/loopback. External LAN devices only connect to Nginx on port 8080.
* **Network Trust:** Plaintext HTTP traffic on LAN networks is visible to other devices on the same Wi-Fi. Limit LAN testing to trusted private networks.

### 8.3 Profile 3: Cloud / S3 Mode (Optional Cloud Storage)
If you decide to scale or transition from local storage to cloud object storage (AWS S3, Cloudflare R2, or MinIO), CareerBridge supports seamless switching without changing application code.

In `.env`, configure:

```env
AWS_SECRET_ACCESS_KEY=your_secret_access_key
```

### 8.4 Profile 4: Mode C — Optional Remote Access via Cloudflare Tunnel

CareerBridge provides an optional, zero-cost remote ingress overlay using Cloudflare Tunnel (`cloudflared`). This allows operators to demonstrate or access CareerBridge remotely over encrypted HTTPS without opening inbound router firewall ports, exposing home IP addresses, or directly publishing backend and database containers.

```
                      [ Remote Client Browser ]
                                 │
                                 ▼ HTTPS (Port 443)
                  ┌──────────────────────────────┐
                  │   Cloudflare Edge Network    │
                  │   - Automatic TLS & DDoS     │
                  │   - WebSocket proxying       │
                  └──────────────┬───────────────┘
                                 │
                                 ▼ Outbound Encrypted QUIC/HTTP2 Tunnel
                  ┌──────────────────────────────┐
                  │   cloudflared (overlay)      │
                  │   - Outbound-only tunnel     │
                  │   - 0 inbound router ports   │
                  └──────────────┬───────────────┘
                                 │
                                 ▼ Internal Docker Network (http://frontend:80)
                  ┌──────────────────────────────┐
                  │   frontend (nginx:alpine)    │
                  │   - Single Ingress Edge      │
                  │   - Proxies /api/*, /health  │
                  └──────────────┬───────────────┘
                                 │
                                 ▼ Internal Docker Network (http://backend:8000)
                  ┌──────────────────────────────┐
                  │   backend (FastAPI/Uvicorn)  │
                  │   - Loopback only on host    │
                  └──────────────┬───────────────┘
                                 │
                                 ▼ Internal Docker Network (port 5432)
                  ┌──────────────────────────────┐
                  │   db (PostgreSQL 16)         │
                  │   - 0 host ports exposed     │
                  └──────────────────────────────┘
```

#### Security Boundaries & Privacy Invariants:
* **Remains Host-Private:**
  * **PostgreSQL (Port 5432):** Zero host ports published; accessible only on the internal Docker bridge network.
  * **FastAPI Backend (Port 8000):** Bound strictly to `127.0.0.1` on the host; completely unreachable from the external Internet.
  * **Secrets & Credentials:** `POSTGRES_PASSWORD`, `JWT_SECRET_KEY`, `GOOGLE_CLIENT_ID`, `SMTP_PASSWORD`, and `TUNNEL_TOKEN` remain in local `.env` and are never exposed over the tunnel or committed to Git.
* **Public Edge:**
  * Only the frontend/Nginx reverse proxy is exposed through the tunnel.
  * Cloudflare terminates TLS and proxies requests to `http://frontend:80`.
  * **Application Security:** Cloudflare does **not** replace application authentication. CareerBridge's JWT authentication, role-based access control (RBAC), and sliding-window rate limiters remain solely responsible for application security.

#### C1. Quick Tunnel (Temporary Development & Ad-Hoc Demo)

Quick Tunnel provides immediate, ephemeral HTTPS access for quick testing or ad-hoc recruiter demonstrations without requiring a Cloudflare account or registered domain.

* **Characteristics:**
  * Generates a temporary `https://<random-id>.trycloudflare.com` URL.
  * Active only while the `cloudflared` container process is running.
  * Changes hostname every session (not suitable for permanent bookmarking).
  * **Authentication:** Standard Email/Password login works normally. Google OAuth is **not supported** out of the box because Google Cloud Console requires fixed origin URLs.
  * **Access Control:** Cloudflare supports optional email-based PIN protection using `--allowed-mail`.
* **Execution via Docker Network:**
  Because `frontend` is an internal Docker service hostname, `cloudflared` must run within the same Docker Compose network:

  **PowerShell (Windows):**
  ```powershell
  # Discover the active Compose network for the running frontend
  $network = (docker inspect (docker compose -f docker-compose.production.yml ps -q frontend) | ConvertFrom-Json).NetworkSettings.Networks.PSObject.Properties.Name | Select-Object -First 1

  # Launch temporary quick tunnel container attached to the frontend network
  docker run --rm -it --network $network cloudflare/cloudflared:latest tunnel --url http://frontend:80

  # Optional: Ephemeral quick tunnel protected by email one-time PIN
  docker run --rm -it --network $network cloudflare/cloudflared:latest tunnel --url http://frontend:80 --allowed-mail interviewer@example.com
  ```

  **Bash (Linux / macOS):**
  ```bash
  # Discover the active Compose network for the running frontend
  NETWORK=$(docker inspect $(docker compose -f docker-compose.production.yml ps -q frontend) --format '{{range $k, $v := .NetworkSettings.Networks}}{{$k}}{{end}}')

  # Launch temporary quick tunnel container attached to the frontend network
  docker run --rm -it --network "$NETWORK" cloudflare/cloudflared:latest tunnel --url http://frontend:80

  # Optional: Ephemeral quick tunnel protected by email one-time PIN
  docker run --rm -it --network "$NETWORK" cloudflare/cloudflared:latest tunnel --url http://frontend:80 --allowed-mail interviewer@example.com
  ```
  *(Quick Tunnel is an ad-hoc CLI tool and does not require putting credentials in `.env`.)*

#### C2. Managed / Named Tunnel (Persistent Remote Access)

Named Tunnels provide persistent remote access and demonstration ingress on your own domain or subdomain (e.g., `https://careerbridge.yourdomain.com`).

> [!NOTE]
> A managed tunnel provides persistent remote network ingress, while full production readiness also depends on host hardening, automated backups, operational monitoring, disaster recovery, domain security, and operational practices.

* **Characteristics:**
  * Stable, permanent HTTPS hostname.
  * Automatically starts and recovers via the `docker-compose.tunnel.yml` overlay.
  * **Google OAuth Compatible:** The stable URL can be registered in Google Cloud Console under *Authorized JavaScript Origins* and *Authorized redirect URIs*.
* **Setup Steps:**
  1. Create a Cloudflare account and configure your domain.
  2. In **Cloudflare Zero Trust Dashboard** → **Networks** → **Tunnels**, create a new tunnel named `careerbridge-production`.
  3. Under **Public Hostname**, map your domain (e.g. `careerbridge.yourdomain.com`) to the service:
     * **Service Type:** `HTTP`
     * **URL:** `frontend:80` *(targets the Nginx container inside the Docker network)*
  4. Copy the generated Tunnel Token and paste it into your local `.env`:
     ```env
     TUNNEL_TOKEN=eyJhIjoiYm...your_actual_token_here...
     ```
  5. Launch the combined base stack plus the tunnel overlay:
     ```bash
     # Linux / macOS / PowerShell
     docker compose -f docker-compose.production.yml -f docker-compose.tunnel.yml up -d
     ```
* **Network Routing & Validation:**
  The Compose configuration places `cloudflared` on the same Docker network as `frontend`, so Docker service-name routing to `frontend:80` is configured correctly. Actual runtime connectivity is validated separately when the optional tunnel is intentionally started.
* **Tunnel-Only Lifecycle Management:**
  * To stop only the tunnel without interrupting local services:
    ```bash
    docker compose -f docker-compose.production.yml -f docker-compose.tunnel.yml stop cloudflared
    docker compose -f docker-compose.production.yml -f docker-compose.tunnel.yml rm -f cloudflared
    ```
  * To shut down the full stack (application + tunnel):
    ```bash
    docker compose -f docker-compose.production.yml -f docker-compose.tunnel.yml down
    ```
  * Local access via `http://localhost` or `http://127.0.0.1` remains 100% operational regardless of tunnel state.

## 9. Troubleshooting & FAQ

| Problem | Root Cause | Solution |
| :--- | :--- | :--- |
| **`Bind for 0.0.0.0:80 failed: port is already allocated`** | Another service on the host (IIS, Apache, Skype, Nginx) is bound to port 80. | Change `FRONTEND_PORT=8080` in `.env` and access via `http://localhost:8080`. |
| **Backend container fails with `ProductionConfigurationError`** | Insecure production configuration detected by `security_validator.py`. | Inspect logs: `docker compose -f docker-compose.production.yml logs backend`. Ensure `DEBUG=False`, `JWT_SECRET_KEY` is 32+ characters and non-default, and `UPLOAD_DIR` is non-empty. |
| **`/health/ready` returns 503 `database: unhealthy`** | PostgreSQL is still initializing or password in `.env` does not match the initialized database volume. | Check DB health: `docker compose -f docker-compose.production.yml ps db`. If changing passwords on an existing volume, update PostgreSQL user credentials using `psql` or start with a fresh volume. |
| **`/health/ready` returns 503 `migrations: pending`** | Database schema is behind Alembic migration head. | Execute migrations: `docker compose -f docker-compose.production.yml run --rm backend alembic upgrade head`. |
| **Uploads fail with 400 `Invalid storage path`** | Upload directory traversal or invalid path configuration. | Verify `UPLOAD_DIR=uploads` in `.env`. Ensure volume `careerbridge_uploads_production` is mounted to `/app/uploads`. |
| **Browser displays CORS Error on API requests** | The origin in the browser address bar is not in `BACKEND_CORS_ORIGINS`. | Add the exact URL (including protocol and port, e.g. `http://192.168.1.50:8080`) to `BACKEND_CORS_ORIGINS` in `.env` and restart containers. |
| **502 Bad Gateway on `/api/*`** | Nginx cannot reach backend container on internal port 8000. | Verify backend container is running and healthy: `docker compose -f docker-compose.production.yml ps backend`. |

## 10. Local Backup, Restore & Disaster Recovery Operations

CareerBridge includes native Windows PowerShell tooling for self-hosted operators to capture atomic, SHA-256 verified backup bundles and perform fail-closed restorations without cloud fees.

```
                     [ CareerBridge Backup Bundle ]
                                   │
       ┌───────────────────────────┴───────────────────────────┐
       ▼                                                       ▼
[ Relational State ]                                  [ Storage Filesystem ]
• database.sql (PostgreSQL 16 dump)                   • uploads.tar.gz (/app/uploads)
  - Tables, users, applications                         - Resumes (/resumes)
  - Full schema snapshot                                - Avatars (/profile_images)
                                   │
       ┌───────────────────────────┴───────────────────────────┐
       ▼                                                       ▼
• checksums.sha256 (SHA-256 integrity)                • manifest.json (Metadata & paths)
```

### 10.1 Creating a Consistent Local Backup

The backup tool automatically manages service quiescence to eliminate relational-to-filesystem snapshot drift:

```powershell
# Run full quiesced backup (recommended)
powershell -ExecutionPolicy Bypass -File .\scripts\backup_local.ps1

# Custom target compose file or output directory
powershell -ExecutionPolicy Bypass -File .\scripts\backup_local.ps1 -ComposeFile .\docker-compose.production.yml -BackupDir .\local-backups
```

#### Quiescence Lifecycle & State Invariants:
1. **Initial State Capture:** Records running status of `frontend`, `backend`, and `db`.
2. **Ingress Suspension:** Suspends `backend` and `frontend` to prevent concurrent writes/deletes.
3. **Connection Draining:** Queries PostgreSQL until active client connections reach `0`.
4. **Binary-Safe Extraction:** Uses `docker cp` to extract database dump and compressed upload archive without PowerShell text-encoding corruption.
5. **Guaranteed Service Resumption:** Restores originally running services in a guaranteed `finally` execution block.

---

### 10.2 Restoring from a Backup Bundle

The restore utility enforces pre-flight privilege validation, zip-slip security scanning, staged database creation, catalog-aware rename switching, and automatic rollback on failure:

```powershell
# Interactive restore (prompts for typed confirmation)
powershell -ExecutionPolicy Bypass -File .\scripts\restore_local.ps1 .\local-backups\careerbridge_backup_YYYYMMDD_HHMMSS

# Automated restore (bypasses prompt for scripted recovery)
powershell -ExecutionPolicy Bypass -File .\scripts\restore_local.ps1 .\local-backups\careerbridge_backup_YYYYMMDD_HHMMSS -Force
```

#### Multi-Stage Staged Restoration Workflow:
1. **Pre-Flight Integrity & Privileges:** Verifies SHA-256 hashes against `manifest.json` and asserts PostgreSQL role permissions (`SUPERUSER` or `CREATEDB` + target ownership + session termination).
2. **Pre-Restore Safety Snapshot:** Automatically snapshots current active state to `local-backups/.pre_restore_safety_<op_id>/` before touching live data.
3. **Staged Database Import:** Restores SQL dump into an isolated staging database (`<db>_stage_<op_id>`) and verifies core tables (`users`, `job_postings`, `applications`, `resumes`, `profile_images`).
4. **Staged Uploads Extraction:** Extracts archive into `/app/uploads/.staging_<op_id>/` after scanning for directory traversal (`..`) and absolute paths.
5. **Atomic Rename Switch:** Renames live DB to `<db>_old_<op_id>` and staging DB to `<db>`.
6. **Uploads Directory Replacement:** Preserves live uploads in `/app/uploads/.live_old_<op_id>/` and installs staged directories.
7. **Readiness Verification:** Restarts services and runs deep health probe (`/health/ready`).
8. **Safety Retention:** Preserves `<db>_old_<op_id>` and `.live_old_<op_id>` indefinitely for operator safety (never automatically dropped).

---

### 10.3 Crash Recovery & Fail-Closed Journaling

Restorations are tracked in a durable JSON journal (`local-backups/.restore_journal_<op_id>.json`). If an unexpected power outage or container crash interrupts a restore:

* Upon restart, `restore_local.ps1` reconciles the journal step against the active PostgreSQL catalog (`pg_database`) and filesystem subdirectories.
* **Fail-Closed Guarantee:** If the catalog or filesystem state is ambiguous or unrecognized, the script halts immediately without modifying or deleting any databases or files, requiring operator review.

---

### 10.4 Single-Machine Storage & Hardware Limitations

* **Single-Drive Risk:** Local backup bundles stored under `local-backups/` reside on the same physical disk as your Docker installation.
* **Disaster Recovery Best Practice:** To protect against complete hardware loss (e.g. SSD failure, theft), operators should periodically synchronize or copy `local-backups/` to an external USB drive or remote off-site location.
